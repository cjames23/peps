Abstract
========

This PEP specifies a new top-level table in ``pyproject.toml`` named
``sources``. The table redirects individual dependencies to other origins (a
local path, a Git repository, a URL, or a specific package index) during
development, without changing the metadata of any distribution the project
builds.

Sources are keyed by project name. A project can declare
``dependencies = ["foo-core"]`` in ``[project]``, which is what consumers of
the published wheel resolve, and separately declare that in this checkout
``foo-core`` is satisfied by the sibling directory ``libs/core``.


Motivation
==========

There is no standard way to say that a dependency should come from somewhere
other than an index while a project is being developed. Several project
managers have added their own tables for this, and none of them read each
other's.

Multi-package repositories
--------------------------

Consider a repository with the following layout, which is a common shape for
a Python monorepo::

    foo/
    ├── libs/
    │   ├── core/
    │   │   └── pyproject.toml     # foo-core
    │   └── client/
    │       └── pyproject.toml     # foo-client
    └── services/
        └── api/
            └── pyproject.toml     # foo-api

``foo-api`` depends on ``foo-client``, which depends on ``foo-core``. A
developer working in this repository expects ``foo-api`` to be built and
tested against the working tree of its siblings rather than against whatever
is published on an index. There are four ways to arrange this today.

1. Put a direct reference in ``[project.dependencies]``, such as
   ``foo-client @ file:///home/dev/foo/libs/client``. This works locally, but
   the absolute, machine-specific path is written verbatim into
   ``Requires-Dist``, and the wheel cannot be installed anywhere else.
   :pep:`508` direct references are published metadata, which makes them the
   wrong tool for a development-only redirection, but they are the only
   standardized one.

2. Install the siblings out of band, for example
   ``pip install -e libs/client`` before ``pip install -e services/api``.
   This works, but the relationship is not declared anywhere. It cannot be
   validated, it is invisible to editors and CI, it is not reproducible, and
   it falls back to the published version whenever a step is skipped or run
   out of order.

3. Use a tool-specific table. ``[tool.uv.sources]`` and
   ``[tool.hatch.sources]`` both solve the problem, but neither tool reads the
   other's table, so the layout of the repository ends up written in one
   vendor's syntax.

4. Modify the import path by adding sibling directories to ``sys.path``,
   ``PYTHONPATH``, or ``.pth`` files. This bypasses packaging entirely and
   breaks as soon as anything needs real metadata.

Only the third is both declarative and correct, which is why tools have
converged on it.

Existing implementations
------------------------

Each major project manager handles this differently:

* uv defines ``[tool.uv.sources]``, supporting ``path``, ``git``, ``url``,
  ``index``, and ``workspace`` entries, with marker-, extra-, and
  group-conditional variants.

* Hatch defines ``[tool.hatch.sources]`` and a per-environment
  ``[tool.hatch.envs.<ENV>.sources]``, with the same five kinds, a string
  shorthand for paths, and entry-by-entry inheritance between environments.

* Poetry attaches ``path``/``develop``, ``git``/``branch``/``rev``/``tag``,
  ``url``, and ``source`` keys to entries in ``[tool.poetry.dependencies]``.
  Since Poetry 2.0, when a :pep:`621` ``[project]`` table is present,
  ``tool.poetry.dependencies`` is documented as existing only "to enrich
  ``project.dependencies`` for locking", which is the same division this PEP
  generalizes.

* PDM expresses local and VCS dependencies through direct references together
  with a separate index configuration.

This is the situation that led to :pep:`621` for project metadata and
:pep:`735` for dependency groups: several tools solving one problem in
incompatible ways.

Consequences of the status quo
------------------------------

* Tools other than project managers cannot see the redirection. Editors,
  language servers, test runners, auditors, license scanners, and validators
  can all read ``[project.dependencies]``, but none of them can tell that
  ``foo-client`` comes from ``libs/client`` without supporting each project
  manager's table separately.

* A new contributor cannot get a working checkout with a standards-compliant
  installer, because the information it needs is not anywhere standard.

* A repository that builds with one tool and manages environments with
  another must express the same relationships twice and keep the copies in
  sync.

* Because direct references are the only portable mechanism, projects
  continue to reach for them and continue to publish distributions that
  cannot be installed.


Rationale
=========

Sources do not declare dependencies
-----------------------------------

``[sources]`` does not declare dependencies. It says where dependencies
declared elsewhere should be fetched from. ``[project.dependencies]`` remains
the complete published statement of what a project needs, and the tool that
sets up the development environment applies ``[sources]`` on top of it.

Direct references write development-only paths and URLs into published
metadata. Keeping them in a separate table instead gives this PEP its central
invariant:

    The metadata of a built distribution is identical whether or not a
    ``[sources]`` table is present.

Because of that invariant, a wheel built from a multi-package checkout records
``Requires-Dist: foo-client>=1.2``, which any consumer can resolve, even
though the developer who built it was working against ``libs/client``. It also
means the table can be added to an existing project without changing what that
project publishes.

Why a top-level table rather than a key in ``[project]``
--------------------------------------------------------

``[project]`` is, by :pep:`621`, the set of fields a build backend reads and
translates into core metadata. Sources are never translated into core
metadata, so ``[project.sources]`` would be the only key in that table that
backends must ignore. Existing validators, such as validate-pyproject, also
reject keys in ``[project]`` that the specification does not define.

A repository root often has no ``[project]`` table and holds only
repository-wide configuration such as ``[dependency-groups]``. Sources need to
be declarable there too, which is the same reason :pep:`735` put
``[dependency-groups]`` at the top level.

Why one table covers paths, Git, URLs, and indexes
--------------------------------------------------

Local paths are the multi-package case, but the same need comes up when
tracking an upstream branch before a release, testing against a patched build,
or pulling internal packages from a private index while everything else comes
from PyPI. These are one operation applied to different origins. Both
reference implementations already treat them that way, and splitting them
would mean several tables with identical precedence rules.


Specification
=============

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this
document are to be interpreted as described in :rfc:`2119`. The lowercase
words "required" and "optional" in the field descriptions below are used in
their ordinary sense and carry no special meaning.

This PEP defines a new table in ``pyproject.toml`` named ``sources``. The
table MAY appear in a ``pyproject.toml`` that has no ``[project]`` table, in
which case it governs that file's own dependency groups and does not reach the
projects in any subdirectory.

Each key of ``[sources]`` is the name of a project whose requirements are to
be redirected. Keys MUST be
`valid non-normalized names <https://packaging.python.org/en/latest/specifications/name-normalization/#valid-non-normalized-names>`__
and MUST be
`normalized <https://packaging.python.org/en/latest/specifications/name-normalization/#normalization>`__
before comparison. If two keys are equal after normalization, tools MUST
report an error. Tools SHOULD present the original, non-normalized name to
users.

The value of each key is either a source entry or a non-empty array of source
entries. A bare source entry is equivalent to an array containing that single
entry.

.. code:: toml

    [sources]
    foo-core = { path = "libs/core", editable = true }
    foo-client = "libs/client"
    httpx = { git = "https://github.com/encode/httpx", tag = "0.28.1" }

Source entries
--------------

A source entry is either a string or a table.

A string is shorthand for a path source: ``name = "libs/core"`` is equivalent
to ``name = { path = "libs/core" }``. A string entry MUST NOT be empty.

A table MUST contain exactly one kind key, which selects the kind of source.
The kind keys are ``path``, ``git``, ``url``, and ``index``. A table with no
kind key, or with more than one, is an error and tools MUST reject it.

In addition to the keys defined for its kind, any table entry MAY carry the
selector keys ``marker``, ``extra``, and ``group``, defined in `Selectors`_.

Tools SHOULD warn about any other unrecognized key, so that typos are caught
while leaving room for future extension.

Path sources
''''''''''''

.. code:: toml

    [sources]
    foo-core = { path = "libs/core", editable = true }
    foo-data = { path = "vendor/foo_data-1.0-py3-none-any.whl" }
    foo-plugin = { path = "vendor/monorepo", subdirectory = "plugins/foo" }

``path``
    Required, string, non-empty. A path to a directory containing a project,
    to a wheel, or to a source distribution.

    A relative path MUST be resolved against the directory containing the
    ``pyproject.toml`` in which the table appears, and MUST be interpreted
    with ``/`` as the separator regardless of platform. Relative paths MAY
    traverse above that directory, which is required for repositories in
    which projects are siblings rather than children.

    An absolute path MAY be used, but is not portable between checkouts.
    Authors SHOULD NOT use absolute paths in a table committed to version
    control, and tools SHOULD warn when one is used.

``editable``
    Optional, boolean, default ``false``. When ``true``, the project at
    ``path`` MUST be installed as an editable install per :pep:`660`, and
    ``path`` MUST refer to a directory containing a project. Tools MUST
    report an error if it refers to a wheel or source distribution.

``subdirectory``
    Optional, string. The path, relative to ``path``, of the directory
    containing the project's ``pyproject.toml``. Used when a repository or
    archive contains a project below its root.

Git sources
'''''''''''

.. code:: toml

    [sources]
    httpx = { git = "https://github.com/encode/httpx", tag = "0.28.1" }
    foo-core = { git = "ssh://git@example.com/foo.git", branch = "main",
                  subdirectory = "libs/core" }

``git``
    Required, string, non-empty. The URL of a Git repository. The value MUST
    NOT include the ``git+`` prefix used by :pep:`508` direct references;
    tools add it when constructing a URL.

``rev``, ``tag``, ``branch``
    Optional, string. These keys are mutually exclusive, and tools MUST
    report an error if more than one is present. When none is present, the
    repository's default branch is used.

``subdirectory``
    Optional, string, as for path sources.

Because a ``branch`` is not a fixed revision, tools SHOULD record the resolved
commit in any lock file they produce.

URL sources
'''''''''''

.. code:: toml

    [sources]
    foo-core = { url = "https://files.example.com/foo_core-1.0-py3-none-any.whl" }

``url``
    Required, string, non-empty. The URL of a wheel or source distribution.
    Tools MAY refuse schemes other than ``https``.

``subdirectory``
    Optional, string, meaningful when the URL names an archive containing a
    project below its root.

Index sources
'''''''''''''

.. code:: toml

    [sources]
    foo-core = { index = "https://pypi.internal.example.com/simple" }

``index``
    Required, string, non-empty. The URL of a :pep:`503` simple repository.

An index source does not change the requirement; it constrains where the
requirement may be satisfied from. Tools MUST resolve the named project
exclusively from the given index, and MUST NOT fall back to any other
configured index for that project.

Adding the URL to the set of searched indexes, for example as an additional
``--extra-index-url``, does not satisfy this requirement. Doing so leaves the
project open to dependency confusion, in which a public index serves a
higher-versioned package under the same name and wins resolution. See
`Security Implications`_.

An index source places no constraint on any project other than the one it is
keyed by.

Selectors
---------

Any table entry MAY carry selector keys, which restrict the circumstances
under which the entry applies.

``marker``
    Optional, string. A :pep:`508` environment marker. The entry applies only
    when the marker evaluates to true for the environment being installed
    into.

``extra``
    Optional, string. The entry applies only to occurrences of the
    requirement within the named key of ``[project.optional-dependencies]``.

``group``
    Optional, string. The entry applies only to occurrences of the
    requirement within the named :pep:`735` Dependency Group.

When the value of a key in ``[sources]`` is an array, entries are considered
in order and the first entry whose selectors all match is applied. If no entry
matches, the requirement is not redirected. An entry with no selectors always
matches, so any entry after it can never be applied. Tools SHOULD warn about
such entries.

.. code:: toml

    [sources]
    torch = [
      { index = "https://download.pytorch.org/whl/cu124",
        marker = "sys_platform == 'linux'" },
      { index = "https://download.pytorch.org/whl/cpu" },
    ]

Applying sources
----------------

A source applies to a requirement when the requirement's project name, after
normalization, equals the normalized key of the source, and one of the
source's entries matches under the rules in `Selectors`_.

Sources MUST be applied to requirements appearing in:

* ``project.dependencies``
* ``project.optional-dependencies``
* ``dependency-groups`` (:pep:`735`)

Tools MAY additionally apply sources to development dependency lists of their
own definition, such as per-environment requirement lists.

Sources MUST NOT be applied to ``build-system.requires``. Build requirements
decide which backend builds a distribution, and which version of it. If
sources could redirect them, the same source tree could produce a different
distribution depending on whether ``[sources]`` was honored, which
`Sources and built distributions`_ does not allow. uv currently applies
sources to build requirements by default; see `Reference Implementation`_.

Direct and transitive requirements
''''''''''''''''''''''''''''''''''

Tools MUST apply sources to every requirement encountered while resolving the
current project, not only to the requirements the current project declares
directly.

If ``foo-api`` declares ``foo-client``, and ``foo-client`` in turn declares
``foo-core``, then redirecting only ``foo-client`` to a local path would leave
``foo-core`` to be resolved from an index, silently mixing a local checkout
with a published release. Under this rule, a source for ``foo-core`` declared
by ``foo-api`` applies to that transitive requirement.

This rule concerns which requirements a table may affect. It does not change
which tables are read, which is governed by `Sources are project-local`_: a
tool reads the ``[sources]`` table of the project being developed and no
other.

Extras and markers
''''''''''''''''''

When a source is applied, the extras requested by the original requirement
MUST be preserved. The original requirement's own environment marker MUST
continue to determine whether the requirement is installed at all. Applying a
source never causes a requirement to be installed in an environment where it
would otherwise be skipped.

Version specifiers
''''''''''''''''''

Path, Git, and URL sources identify a distribution directly, so the
requirement's version specifier no longer takes part in resolution. Tools
SHOULD check that the version obtained satisfies the original specifier, and
SHOULD report an error if it does not; a mismatch usually means the specifier
or the source is out of date. An index source does not bypass resolution, so
its version specifier still applies.

Precedence
----------

A requirement that already carries a :pep:`508` direct reference
(``name @ url``) MUST NOT be redirected. The explicit URL written on the
requirement takes precedence over any matching source, and tools SHOULD warn
that the source was not applied.

When a tool reads sources from more than one location, for example a
project-wide table and a per-environment table, it MUST merge them entry by
entry, with the more specific location replacing individual entries of the
less specific one rather than replacing the table wholesale. Names are
compared after normalization for the purpose of this merge.

Sources are project-local
-------------------------

Tools MUST read the ``[sources]`` table only from the ``pyproject.toml`` of
the project currently being developed. In particular:

* A ``[sources]`` table present in a source tree or source distribution
  obtained as a dependency MUST NOT be honored.

* A ``[sources]`` table is not inherited from a parent directory. Tools MUST
  NOT search ancestor directories for further tables to merge.

The first rule exists for security reasons. Without it, any package on any
index could redirect the dependencies of every project that installs it. See
`Security Implications`_.

Sources and built distributions
-------------------------------

Build backends MUST NOT read the ``[sources]`` table, and tools MUST NOT use
it to alter the contents of a built distribution. The core metadata produced
for a project MUST be identical whether or not the table is present.

The table is part of ``pyproject.toml`` and will therefore appear in source
distributions. Consumers of such a source distribution MUST ignore it, per
`Sources are project-local`_.

Disabling sources
-----------------

Tools that consume ``[sources]`` MUST provide a documented way to ignore the
table entirely, and SHOULD spell the command-line option ``--no-sources``.

This lets a project check that the dependencies it publishes resolve on their
own, without the redirections that make a development checkout work. Such a
check belongs in the release pipeline of any repository that uses sources.

Reporting
---------

An unmatched source does nothing, so a typo in a key shows up only as the
wrong distribution being installed. Tools SHOULD warn about entries matching
no requirement, and SHOULD provide a way to display, for each requirement,
which source was applied and what it resolved to.

Interaction with lock files
---------------------------

Sources are an input to resolution, and a :pep:`751` ``pylock.toml`` is an
output. Because ``pylock.toml`` already records concrete origins (``vcs``,
``directory``, ``archive``, and ``index``), a lock file generated with sources
applied needs no change to the format. Such a lock file is not interchangeable
with one generated without sources, and tools that can produce both SHOULD
write them to separate ``pylock.<name>.toml`` files.


Examples
========

A multi-package repository
--------------------------

Each project declares the requirements it needs in terms that hold for anyone
installing it from an index, and separately declares where those requirements
are satisfied from within this checkout. Paths are relative to the directory
containing each ``pyproject.toml``.

.. code:: toml

    # foo/libs/client/pyproject.toml
    [project]
    name = "foo-client"
    version = "1.4.0"
    dependencies = ["foo-core>=1.0", "httpx>=0.28"]

    [sources]
    foo-core = { path = "../core", editable = true }

.. code:: toml

    # foo/services/api/pyproject.toml
    [project]
    name = "foo-api"
    version = "2.1.0"
    dependencies = ["foo-client>=1.2", "fastapi>=0.115"]

    [sources]
    foo-client = { path = "../../libs/client", editable = true }
    foo-core = { path = "../../libs/core", editable = true }

``foo-api`` lists ``foo-core`` as well as ``foo-client``. It has to, because
``foo-core`` reaches ``foo-api`` through ``foo-client``, and tables are not
inherited between projects (see `Direct and transitive requirements`_). The
wheel built from ``foo-api`` still records ``Requires-Dist: foo-client>=1.2``.
Installing that wheel from an index gets ``foo-client`` from the index;
installing the checkout with a tool that supports ``[sources]`` gets it from
``libs/client``.

Tracking an upstream branch
---------------------------

.. code:: toml

    [project]
    dependencies = ["httpx>=0.28"]

    [sources]
    httpx = { git = "https://github.com/encode/httpx", branch = "master" }

The project continues to advertise ``httpx>=0.28`` to its consumers while its
developers test against unreleased upstream changes, and removing the source
entry switches back to the published release.

A private index for internal packages
-------------------------------------

.. code:: toml

    [project]
    dependencies = ["foo-core>=1.0", "requests>=2.32"]

    [sources]
    foo-core = { index = "https://pypi.internal.example.com/simple" }

``foo-core`` resolves only from the internal index while ``requests``
resolves from the default index, and neither index can supply the other's
package.


Backwards Compatibility
=======================

``[sources]`` is a new top-level table. :pep:`518` reserved ``[tool]`` for
tool-specific configuration and left the remainder of the top-level namespace
for standardization, which :pep:`735` subsequently used for
``[dependency-groups]``. Existing ``pyproject.toml`` files are unaffected.

A tool that does not implement this PEP ignores the table and resolves every
requirement from its configured indexes. In a multi-package repository this
usually produces a clear failure, because the sibling projects are not
published. It can also produce a silent difference, when the project is
published and the installed release is not the working tree. The same is true
today of ``[tool.uv.sources]`` and ``[tool.hatch.sources]`` for any tool that
does not read them. The proposal does not introduce a new kind of failure, and
by increasing the number of tools that understand the declaration, it makes
the existing one less common.

Migration from tool-specific tables
-----------------------------------

Tools that already provide an equivalent table SHOULD support both. The
recommended behavior is to treat the standard ``[sources]`` table as the base
and the tool-specific table as an override applied entry by entry, warning
when both define the same normalized name, so that a repository can migrate
incrementally.

Audit and update
----------------

The following would need updating:

* Validators and schema definitions for ``pyproject.toml``.
* Editors and language servers that resolve imports between projects in one
  repository.
* Dependency auditing and license tools, which cannot currently tell that a
  requirement is satisfied locally.
* Documentation for the existing implementations.


Security Implications
=====================

Sources decide where installed code comes from. A source that points at a
project directory, a Git repository, or a source distribution also causes that
code to be built, which can run arbitrary code.

Sources in dependencies
-----------------------

If tools honored ``[sources]`` tables found in dependencies, any package on
any index could ship a table redirecting ``requests``, or any other name, to a
URL it controls, for every project that installs it. The rule in
`Sources are project-local`_ prevents this, which is why it is a MUST. It
limits which tables are read, not which requirements a table can affect: a
project's own table can still redirect a transitive requirement (see
`Direct and transitive requirements`_).

Dependency confusion
--------------------

An implementation that handles an index source by adding its URL to the
searched indexes exposes the project to dependency confusion, because a public
index can serve a higher version under the same name and win resolution.
Requiring that the project resolve only from the named index closes that gap,
and makes index sources safer than the ``--extra-index-url`` invocations they
replace.

Reviewing sources
-----------------

A Git or URL source can point anywhere, and a path source can point outside
the repository. Direct references already allow the same, but a ``[sources]``
table is short and easy to skim past in review. Tools SHOULD show the resolved
absolute location of each applied source, especially when a relative path
leads outside the directory containing the ``pyproject.toml``.


How to Teach This
=================

The key distinction is between what a package requires, which is published in
``[project]``, and where those requirements come from during development,
which stays in the repository and lives in ``[sources]``.

The example in `Examples`_ is a good starting point: declare the requirement
in ``[project]``, declare the local path in ``[sources]``, and check that the
built wheel is unchanged. Users should know that a project has to redirect
every in-repository package it depends on, including indirect ones, and that
``--no-sources`` shows what a consumer of the package will see, which makes it
easy to check in CI that the published dependencies still resolve.

Projects that currently write ``name @ file:///...`` into
``[project.dependencies]`` should move that redirection into ``[sources]``.


Reference Implementation
========================

`uv <https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-sources>`__
implements this design as ``[tool.uv.sources]``, including marker-, extra-,
and group-conditional entries and a ``--no-sources`` option.
`Hatch <https://hatch.pypa.io/latest/config/environment/sources/>`__
implements it as ``[tool.hatch.sources]``, including the string shorthand and
per-environment tables.

Neither matches this PEP exactly. uv names indexes rather than taking URLs,
does not accept the string shorthand, and applies sources to
``build-system.requires``. Hatch adds index sources as extra indexes rather
than restricting resolution to them, and defaults ``editable`` to ``true``.
Both also support a ``workspace`` kind, which this PEP does not define. A
prototype of this PEP in Hatch is planned alongside its discussion.


Rejected Ideas
==============

Leave it in ``[tool]``
----------------------

Leaving this in ``[tool]`` works for repositories that use one tool. It does
nothing for repositories that use more than one, or for editors, auditors, and
other tools that need to understand a checkout without supporting every
project manager's table.

Extend the dependency specifier syntax instead
----------------------------------------------

Allowing ``foo-core @ ../libs/core`` in ``[project.dependencies]`` would put
the redirection where the dependency already is, but it would put it in
published metadata, which is the problem this PEP exists to solve. It would
also require changing :pep:`508`, and therefore every parser of every
dependency specifier in the ecosystem, in order to express something that has
no meaning outside the authoring repository.

Let sources affect published metadata
-------------------------------------

Some projects do want to publish a distribution that depends on a Git
revision. :pep:`508` direct references already cover that, and they are the
right tool because they are published and visible to consumers. If
``[sources]`` could sometimes affect published metadata, it would lose the
property that makes it safe to add to an existing project.

Inherit sources from ancestor directories
-----------------------------------------

Letting a project inherit ``[sources]`` from the nearest ancestor
``pyproject.toml`` would save each project from repeating the same entries.
We rejected it because upward search has no natural stopping point: a stray
``pyproject.toml`` in a home directory would silently change resolution for
every project below it, and the only obvious boundary, a version control root,
is outside packaging.
